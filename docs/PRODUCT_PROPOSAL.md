# Продуктовое предложение: развитие главного экрана Дзена

## Контекст и цель

В рамках тестового задания выбран мобильный интерфейс Дзена. Цель концепта — показать, как можно развить существующий интерфейс через три точечных изменения: сделать короткие видео заметнее, упростить инструменты автора и повысить визуальную заметность новостей.

Это продуктовые гипотезы, а не утверждения о подтверждённых проблемах или текущих показателях Дзена. Для проверки потребуются реальные пользовательские данные и исследование.

## 1. Короткие вертикальные видео в верхней части главной

### Гипотеза

Если разместить блок коротких вертикальных видео сразу после категорий, больше пользователей заметят этот формат и начнут просмотр, поскольку контент будет доступен без поиска в общей ленте.

### Решение

- Горизонтальная карусель вертикальных обложек сразу под категориями.
- На карточке отображаются обложка, название, автор и длительность.
- Нажатие открывает отдельный сценарий просмотра.
- Обычная лента остаётся ниже, чтобы короткие ролики не вытесняли другие форматы.

### Метрики

**Основная:** Video Start Rate — доля пользователей, которым показали блок и которые запустили хотя бы одно видео.

**Дополнительные:** CTR блока, среднее время просмотра, процент досмотров, количество просмотренных роликов за сессию, D1/D7 Retention.

**Защитные метрики:** взаимодействие с обычной лентой, быстрые возвраты из просмотра, скрытия/пропуски блока. Рост времени просмотра сам по себе не считается успехом, если ухудшается потребление других форматов или удовлетворённость.

## 2. Студия автора

### Гипотеза

Если собрать основные инструменты автора в едином разделе, пользователям будет проще управлять каналом, создавать материалы и отслеживать их результаты.

### Решение

Создать отдельный экран «Студия автора», доступный из нижней навигации и меню профиля. В него входят:

- обзор канала и ключевые показатели;
- список опубликованных материалов и черновиков;
- создание статьи, поста или видео;
- переход к редактированию публикаций;
- аналитика просмотров, аудитории и вовлечённости;
- настройки канала.

### Метрики

**Основная:** Task Completion Rate — доля авторов, успешно завершивших целевой сценарий (например, создание и публикацию материала).

**Дополнительные:** медианное время выполнения сценария, Draft-to-Publish Conversion, количество публикаций на активного автора, WAU авторов.

**Защитные метрики:** ошибки при публикации, доля незавершённых форм, обращения в поддержку по вопросам управления каналом.

## 3. Миниатюры в блоке быстрых новостей

### Гипотеза

Если сопровождать короткие новости небольшими тематическими изображениями, пользователям будет проще сканировать список и выбирать интересующие материалы.

### Решение

Компактная строка новости содержит миниатюру, заголовок, источник, время публикации и визуальный индикатор перехода. Размер изображения ограничен, чтобы карточки оставались компактными и не перегружали экран.

### Метрики

**Основная:** CTR новостных карточек — доля показов карточек, завершившихся открытием новости.

**Дополнительные:** количество открытых новостей на пользователя, время до первого открытия, глубина просмотра блока.

**Защитные метрики:** скорость загрузки блока, доля ошибок изображений, пропуски и скрытия новостного блока.

## План проверки гипотез

Предлагается A/B-тестирование:

- **Контрольная группа A:** текущий вариант интерфейса.
- **Экспериментальная группа B:** интерфейс с выбранными изменениями.

До эксперимента необходимо зафиксировать базовые значения метрик, определить целевую аудиторию, длительность и минимально значимый эффект. Группы должны быть сопоставимы, а период наблюдения — одинаковым. После запуска проверяются статистическая значимость изменений и защитные метрики.

Не следует заранее указывать вымышленные проценты роста. Численные целевые значения устанавливаются после получения базовой аналитики и расчёта необходимой выборки.

## События аналитики

Для проверки гипотез предлагается фиксировать ключевые действия пользователей. Названия событий приведены как пример схемы аналитики для будущей реализации; в текущем прототипе отправка событий на сервер не настроена.

| Событие | Когда фиксируется | Основные параметры |
| --- | --- | --- |
| `video_block_view` | Блок коротких видео попал в видимую область экрана | `user_id`, `session_id`, `block_position`, `timestamp` |
| `video_card_click` | Пользователь нажал на карточку видео | `video_id`, `position`, `source_block` |
| `video_start` | Воспроизведение видео фактически началось | `video_id`, `author_id`, `position` |
| `video_complete` | Пользователь досмотрел видео до конца | `video_id`, `watch_duration`, `video_duration` |
| `studio_open` | Автор открыл «Студию автора» | `user_id`, `entry_point` |
| `publication_start` | Автор начал создавать новую публикацию | `content_type`, `entry_point` |
| `publication_success` | Публикация успешно сохранена или опубликована | `content_id`, `content_type`, `publication_status` |
| `news_card_view` | Новостная карточка попала в видимую область экрана | `news_id`, `position`, `source_block` |
| `news_card_click` | Пользователь открыл новость нажатием на карточку | `news_id`, `position`, `source_block` |

### Правила сбора данных

- Показ (`*_view`) следует фиксировать, когда элемент действительно становится видимым пользователю, а не просто при загрузке страницы.
- Клик и фактическое начало воспроизведения — разные события: нажатие на видео не гарантирует, что оно запустилось.
- Для расчёта CTR необходимо заранее согласовать единицу подсчёта: показы карточек или уникальные пользователи, увидевшие карточку. В рамках этого предложения CTR считается как открытия карточек, разделённые на их валидные показы.
- Для расчёта Completion Rate событие досмотра должно отправляться один раз при достижении конца ролика; повторные просмотры учитываются отдельно.
- В событиях не следует передавать персональные данные, не нужные для анализа продуктовой гипотезы.

Эта схема задаёт минимальный набор событий для оценки предложенных изменений. Перед внедрением её необходимо согласовать с аналитиком и адаптировать к принятой в продукте системе событий.

## Сценарии прототипа

1. **Читатель:** открывает главную → замечает короткие видео → выбирает карточку → попадает на экран просмотра.
2. **Читатель новостей:** видит компактный блок с изображениями → выбирает новость → открывает экран материала.
3. **Автор:** открывает «Студию автора» → изучает обзор канала → переходит к публикациям или аналитике → создаёт/редактирует материал.

## Объём реализации и ограничения

В прототипе реализованы интерфейсные состояния и переходы между экранами. Не реализованы серверное хранение, авторизация, реальное воспроизведение видео, контентный API и сбор аналитики. Значения в студии автора и карточках являются демонстрационными.

## Ожидаемый результат

Концепт демонстрирует три направления развития продукта: повышение заметности короткого видео, упрощение авторских сценариев и улучшение визуального сканирования новостей. Результативность каждого изменения должна подтверждаться экспериментом, а не предполагаться по одному макету.
